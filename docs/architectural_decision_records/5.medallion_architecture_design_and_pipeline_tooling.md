## Context
In the previous ADR, we designed the architecture of the data mesh (how it maps to the organization) and the data contracts and governance standards (everything needed to define a high-quality data product). In this ADR, we define how to actually transform raw datasets into high-quality data products, which involves designing in detail the medaillion architecture, dimensional modelling and pipeline tooling that will be used to create high-quality data products.

## Decision
- We use the bronze-silver-gold medallion architecture. This is what constitutes done in each layer:
Each layer has a clear completion criterion. A pipeline stage is done when the following conditions are met and no further work happens in that stage.

| Layer | Permitted transformations | Done when |
|---|---|---|
| Volume | None. Raw file storage only. | File is written to Unity Catalog Volume with provenance metadata (`_source_url`, `_ingestion_timestamp`, `_release_version`). No reading, parsing or conversion yet. |
| Bronze | Format conversion to Delta only. No filtering, no field renaming, no type casting beyond what Delta requires. Metadata columns added. | Raw source is faithfully represented as a queryable Delta table. Schema preserved as-is. All fields stored as string or binary where type is ambiguous. |
| Silver | Domain-local cleaning: null handling, deduplication, type casting, domain-specific filtering, joins within the domain only. No aggregation. | One validated, non-aggregated record per source entity. GX validation suite passes. No records silently dropped — quarantine table written for rejects. |
| Gold | Aggregation, score computation, cross-source joins within the domain, feature engineering. Final consumer-facing schema applied. | Data contract quality rules pass. Table properties stamped. GRANT executed to consumer groups. |

Bronze should only hold raw, immutable data with minimal metadata. Silver is where cleansing, standardisation, and schema enforcement happen without losing granularity. Gold is for aggregated, business-facing models.

- We adopt a Volume first pattern for scientific data.
Scientific source files that cannot be directly ingested as Delta (VCF, FASTQ, instrument-native formats, bulk Parquet archives from public databases) are stored first in a Unity Catalog Volume, then converted to a Bronze Delta table. The only transformation in the Volume → Bronze step is format conversion.
Storing files in Volumes first also means raw files are available for reprocessing without re-downloading from source — important for versioned public databases where a release may be superseded.


- Silver layer is Domain local.
Silver is a domain-local clean layer. It does not join across domain catalogs. It may join within the domain — for example, joining a targets table with a GTEx expression table where both are bronze sources owned by the same domain.
The enterprise view is assembled at gold layer by each domain, or in the hub catalog for shared reference data. This is a deliberate data mesh choice: data product owners are accountable for quality, usability, and alignment with business goals and they can only be accountable for data they understand and control. Allowing silver to join across domains would create hidden dependencies between domain owners before either has validated their data.


- Bronze, silver, and gold map to schemas within a domain catalog. Each domain gets its own isolated medallion stack.
```
neuroscience (workspace)
├── discovery (catalog)
│   ├── bronze (schema)    ← pipeline-sa write access only
│   ├── silver (schema)    ← pipeline-sa write, domain scientists read
│   └── gold (schema)      ← published data product, consumer groups read
├── translational_science (catalog)
│   ├── bronze / silver / gold
...
└── hub (catalog)
    └── reference (schema) ← shared ontologies, gene lists, disease taxonomies
```
Access is tiered by layer: bronze is highly restricted (pipeline service principals only), silver is accessible to domain scientists and power users, gold is accessible to declared consumer groups across domains

- Only Gold tables can be consumed cross-domain.
Domains may only consume gold tables from other domains. Silver and bronze tables are not accessible outside the owning domain's service principal. This is enforced via Unity Catalog grants — consumer group grants exist only on gold schemas.
The rationale is domain ownership: the whole logic of data mesh is that domain owners who best understand the data are responsible for cleaning it before others consume it.

- Shared reference data that no single domain owns (gene ontologies, disease taxonomies, standard identifiers) lives in hub.reference and follows the same gold-only rule — it is published as a validated reference data product, not a raw source.

- Databricks Jobs with Python wheel tasks is the chosen pipeline tooling. DLT is explicitly not used for the following reasons: familiarity reduces debugging overhead on a single-person project; DLT notebooks cannot be run directly and require a full workflow start to see output, slowing iteration; and equivalent data quality standards are achievable through Great Expectations integrated as a pipeline task.
```
bronze_ingestion → silver_transform → validate_gx → publish_gold
```

- Hub and domain data product owners both provide quality enforcement mechanisms, but the domain data product owners remain sole responsible.
    - Hub test framework (scheduled, generic): Runs structural tests and contract-compliance tests against all gold tables on a weekly schedule. Catches schema drift, permission drift, contract metadata staleness, and cross-release volume regressions. Does not validate scientific assumptions.
    - Domain pipeline GX (per-run, scientific): Runs inside validate_gx before publish_gold. The data product owner is responsible for maintaining and extending these tests. GX failure halts execution before the gold table is written. No staging table is created — the pipeline stop itself is the gate. This avoids duplicating the dataset into a tested staging version and a promoted final version, which would add an unnecessary fourth layer on top of bronze/silver/gold.
    Scientific assumption tests — filter thresholds, join validity, biological correctness of derived fields — are the sole responsibility of the domain data product owner and are not generated by the hub framework.
- Pipeline failures are handled differently per governance tier
Failure handling differs by governance tier because the consequences of bad data differ.
| Tier | GX failure in validate_gx | Upstream source unavailable | Unexpected schema change |
|---|---|---|---|
| Exploratory (Discovery, Translational Science) | Warn and quarantine. Bad records written to `[domain].bronze.[table]_quarantine`. Pipeline continues to gold with valid records only. Acceptable because gold-only consumers do not see quarantined records. | Fail job, alert owner. Previous gold version remains queryable via Delta time travel. | Fail at bronze. Schema-as-string policy means most changes are absorbed; structural changes require manual review before reprocessing. |
| GLP-ready (Translational Medicine, GLP-bound Discovery) | Hard fail. Pipeline halts. No partial gold write. Owner must review quarantine before re-run. | Fail job, alert owner and ELN system. Previous gold version remains. | Hard fail. Schema changes in GLP-bound data require SOP-documented review before reprocessing. |
| Regulatory (Clinical Development, Biostatistics, Regulatory) | Hard fail. Pipeline halts. Failure logged to immutable audit trail in Unity Catalog system tables. Owner and Regulatory Affairs notified. | Hard fail with regulatory escalation. Data gaps in submission-bound pipelines require documented deviation. | Hard fail with documented change control. CDISC version changes require formal amendment to study-specific mapping specifications. |

- All pipelines must be idempotent. Running the same pipeline twice with the same inputs produces the same output. This is required for:

Reproducibility: a FAIR commitment made in ADR-001
Regulatory: submission-bound pipelines must produce identical results on re-run for audit purposes
Debugging: failed runs can be retried without manual cleanup

Idempotency is implemented by:

Versioned bulk sources (OpenTargets, ClinVar): bronze writes use mode("overwrite") with release version as a parameter. Re-running with the same release version produces the same bronze table.
API-incremental sources (ClinicalTrials.gov): bronze uses append-only writes with a deduplication key ([source_id, ingested_date]). Silver deduplicates before writing. Re-running within a day produces the same silver output.
Gold: always written with mode("overwrite"). Previous version accessible via Delta time travel.

- Data retention time is also handled differently per governance tier:
Best practice establishes retention periods based on regulatory requirements and analytical needs rather than storage considerations alone. V4c Delta Lake table history is controlled by delta.logRetentionDuration (default 30 days) and delta.deletedFileRetentionDuration (default 7 days). Databricks Documentation Both defaults are insufficient for this platform.
| Tier | logRetentionDuration | deletedFileRetentionDuration | Rationale |
|---|---|---|---|
| Exploratory | 90 days | 90 days | Sufficient for debugging and quarterly release cycles |
| GLP-ready | 1 year | 1 year | Covers study duration for most early-phase programs |
| Regulatory | 25 years | 25 years | ICH E6 GCP mandate — matches archival requirement in ADR-003 |
Note: Delta time travel retention for regulatory-tier tables does not substitute for formal archival in an FDA-validated system. The 25-year logRetentionDuration ensures Delta lineage is queryable during the retention period; the validated archival system (SAS XPT format, per ADR-003) is the compliance record.

# Data Contracts and Governance Standards

## Date
2026-04-18

## Author
Steff Horemans 

## Context
In the previous ADR, we designed the architecture of the data mesh. We clearly designated the broad responsibilities of the spoke owners and of the Hub owners. In it, it was decided that the Hub owners are responsible for providing data contract templates and the spoke owners were responsible for filling it in. In this ADR, we will define how to define data contracts that adhere to any organizational constraints.
A data product is considered a product that facilitates an end-goal through the use of data. It can be anything from tables, to ML models to Dashboards. A good data product has the following attributes:
- **Quality and observability**: Trusted data asset includes accuracy, accessibility, timeliness, consistency, reliability and good documentation. Defined quality metrics that are monitored over time.
- **Semantic consistency**: Compliant with business rules and terminology
- **Privacy**: Ability to anonimize sensitive information (anonymization, encryption, data residency, PII tagging, ...)
- **Security**: Has defined access policies (who, what, ...) and acceptable use policies.
- **Discoverability**: Published in a central data catalogue so others in the org can find them.

Best practices according to Databricks include:
- Have a clear data product owner that understands both business and technical requirements.
- Define comprehensive data contracts upfront that include quality metrics, schema definitions, usage policies and security parameters to ensure alignment between producers and consumers
- Automate monitoring using Lakehouse Monitoring, setting up alerts for quality metric thresholds to catch issues early.
-  Implement a staged development approach with separate development, testing and production environments to ensure quality before publication.
- When building pipelines, utilize Delta Live Tables (DLT) with quality controls implemented directly in your code, leveraging built-in expectations and constraints to validate data at each stage.
- Document extensively within Unity Catalog, using both technical specifications and business context to help users understand and correctly utilize your data products. 
- For governance efficiency, standardize naming conventions and metadata across data products to improve discoverability and interoperability. 
- Finally, implement a formal feedback loop with consumers to continuously improve your data products based on actual usage patterns and user needs.

## Decision

- At minimum, Databricks guidelines will be followed for data contracts:
        - Data description (name, description, source systems, attribute selection, …)
        - Data schema (tables, columns, anonymization and encryption info, filter, masks, …) and data formats (semi-structured and unstructured data)
        - Usage policies (tags, PII, guidelines, data residency, …)
        - Data quality (applied quality checks and constraints, quality metrics, …)
        - Security (who is allowed to use the data product)
        - Data SLAs (last update, expiration dates, retention time, …)
        - Responsibilities (owner, maintainer, escalation contact, change process, …)
- Data contracts can and will need to be updated by the data product owners with relevant regulatory information for special domains. For example, scientific open-source data does not have the same regulatory requirements as patient PII.
- Data products will be developed using a contract-first approach: Contract templates will be retrieved from Hub repo (see previous ADR) and filled in by the product owner before any coding occurs. Adherence to the contract template will be tested by the Hub team by a github Actions pipeline, but the data product owner remains the primary responsible for contract adherence.
- Data products will be created in Declarative Automation bundles (former Databricks Asset Bundles). DAB's are the units that define a data product.
- Data products will be created in Unity Catalog with the appropriate access controls and metadata added as part of the DAB.
- All data products published to a gold schema must have a data contract conforming to the Open Data Contract Standard (ODCS) v3.1.0, maintained by the Linux Foundation AI & Data Foundation (Bitol). ODCS is chosen because:
    • It is an open standard under Apache 2.0 licence, avoiding vendor lock-in.
    • It natively supports a regulatory SLA driver field, making regulatory sensitivity a first-class concept rather than a custom extension.
    • The datacontract-cli tooling enables automated validation in CI/CD with no additional infrastructure.
    • It is compatible with Databricks' own recommendation to use YAML-based contracts in Unity Catalog environments.
The canonical ODCS repository and schema are available at:
https://github.com/bitol-io/open-data-contract-standard

- The hub repository (neuroscience-hub) maintains a base contract template that all domain contracts extend. The following fields are mandatory for every data product regardless of domain. These are enforced by the validate-contracts GitHub Action on every pull request that touches a contract file.

Field	Required	Purpose
id	✓ Yes	Unique identifier for the data product across the workspace
name, version, domain, status	✓ Yes	Discovery metadata enabling Unity Catalog search and lineage
team (named individual)	✓ Yes	Named data product owner — not a team alias. Accountability requires a person.
schema with field descriptions	✓ Yes	Enables automated test generation and Unity Catalog documentation
quality (≥1 expectation)	✓ Yes	At least one quality check must be declared and enforced
lineage.sources	✓ Yes	Upstream sources — enables cross-domain impact analysis
governance.access_tier	✓ Yes	public | internal | restricted | confidential — drives UC permissions
governance.glp_applicable	✓ Yes	Triggers GLP-specific audit trail requirements when true
governance.submission_bound	✓ Yes	Triggers 25-year retention and UC immutable log when true
provenance.source_version_or_date	✓ Yes	Version pin for reproducibility — required for FAIR compliance
quality_tier.known_limitations	✓ Yes	Non-null honest statement of what this data cannot be used for

Enforcement rule:  known_limitations must be non-empty. A contract with a null known_limitations field fails CI validation. This is the single most important field for preventing downstream misuse of data, particularly the use of exploratory Discovery scores in regulatory submissions.

- Three governance tiers apply within the Neuroscience workspace. The tier is determined by two boolean flags in the contract: glp_applicable and submission_bound. Tier assignment is automatic — no manual configuration is required once the contract is filled in correctly.

Tier	glp_applicable	submission_bound	Retention	Audit trail	Primary domains
Exploratory	false	false	Business decision (default 3yr)	Unity Catalog system tables	Discovery, Translational Science
GLP-ready	true	false	Study-dependent (typically 10yr)	UC system tables + ELN linkage	Discovery (submission-bound experiments), Translational Medicine
Regulatory	true	true	25 years (ICH E6 GCP mandate)	UC immutable audit log + define.xml	Clinical Development, Biostatistics, Regulatory Affairs

Constraint:  submission_bound: true requires glp_applicable: true. A contract that declares submission_bound without glp_applicable fails CI validation. The hub check_hub_fields.py script enforces this automatically.

## Consequences
**Positive consequences**
    • Domain teams get structural and contract compliance tests for free by filling in the ODCS contract correctly. The contract becomes executable specification.
    • Permission drift is detectable and correctable via the weekly audit action, without requiring manual GRANT audits.
    • The known_limitations field, enforced as non-null in CI, creates an explicit record of what each data product cannot be used for. This is the primary guard against Discovery scores being cited in regulatory submissions.
    • The glp_applicable and submission_bound flags automatically trigger the correct governance controls without requiring domain owners to understand the full regulatory framework.
    • The hub-spoke architecture means governance improvements propagate to all domains: when the hub adds a new mandatory contract field, all domain PR pipelines begin enforcing it on their next pull request.

**Risks and mitigations**

Risk	Mitigation	Residual risk
Domain owners fill contracts mechanically without understanding the fields, particularly known_limitations	CI rejects null known_limitations. AI strategy: AI drafts contracts from pipeline code, human reviews and accepts. PR review action checks for boilerplate language.	Medium — cannot fully automate quality of the limitations statement
CDISC standard version mismatch between contract and define.xml	Contract and define.xml generated from same source of truth in Biostatistics pipeline. Hub test framework validates consistency.	Low with automation in place
Hub-generated tests create false confidence by missing edge cases neither the AI nor the engineer considered	Scientific assumption tests written by data product owner are mandatory for spoke repos. Documented in hub README.	Medium — inherent to any testing regime
Permission model becomes stale as team membership changes	Weekly automated audit detects drift. UC group membership managed in IdP, not Databricks directly.	Low with automation in place
Free tier constraint: one workspace means catalog isolation substitutes for workspace isolation	Documented explicitly in uc-permissions/ as an architectural constraint. Revisit if platform scales to clinical patient data, which may require physical workspace separation.	Accepted for demonstrator scope

**Out of scope for this ADR**
    • Medallion architecture layer definitions — covered in ADR-004 (Pipeline Standards)
    • MLflow experiment tracking conventions — covered in ADR-005 (ML Governance)
    • FAIR data principle implementation beyond version pinning and lineage — deferred to a dedicated FAIR ADR
    • 21 CFR Part 11 electronic signature requirements — no patient data in current scope; revisit when Clinical Development ingests trial data
    • Cross-organisational data sharing via Delta Sharing — deferred until external collaboration is required

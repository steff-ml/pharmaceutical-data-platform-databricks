## Date
2026-04-19

## Author

## Context
In the previous ADR, we designed the architecture of the data mesh. We clearly designated the broad responsibilities of the spoke owners and of the Hub owners. In it, it was decided that the Hub owners are responsible for providing data contract templates and the spoke owners were responsible for filling it in. In this ADR, we will define how to define data contracts that adhere to any organizational constraints.
A data product is considered a product that facilitates an end-goal through the use of data. It can be anything from tables, to ML models to Dashboards. A good data product has the following attributes:
- **Quality and observability**: Trusted data asset includes accuracy, accessibility, timeliness, consistency, reliability and good documentation. Defined quality metrics that are monitored over time.
- **Semantic consistency**: Compliant with business rules and terminology
- **Privacy**: Ability to anonymize sensitive information (anonymization, encryption, data residency, PII tagging, ...)
- **Security**: Has defined access policies (who, what, ...) and acceptable use policies.
- **Discoverability**: Published in a central data catalogue so others in the org can find them.

Best practices according to Databricks include:
- Have a clear data product owner that understands both business and technical requirements.
- Define comprehensive data contracts upfront that include quality metrics, schema definitions, usage policies and security parameters to ensure alignment between producers and consumers
- Automate monitoring using Lakehouse Monitoring, setting up alerts for quality metric thresholds to catch issues early.
-  Implement a staged development approach with separate development, testing and production environments to ensure quality before publication.
- When building pipelines, utilize Delta Live Tables (DLT) with quality controls implemented directly in your code, leveraging built-in expectations and constraints to validate data at each stage.
- Document extensively within Unity Catalog, using both technical specifications and business context to help users understand and correctly utilize your data products. 
- For governance efficiency, standardize naming conventions and metadata across data products to improve discoverability and interoperability. 
- Finally, implement a formal feedback loop with consumers to continuously improve your data products based on actual usage patterns and user needs. This is handled in the data_mesh_design DR

In this context, it is important to remember that the data mesh shifts this responsibility for all these things to the data product owners from the domains and that there is a lot to keep in mind to create good data products. To reduce the complexity for the data product owners while maintaining high quality, we can adopt Golden Path engineering. This is a strategy where the platform team provides detailed resources to both enable data product owners AND maintain governance oversight.

## Decision


- All gold-layer data products use ODCS v3.1.0 (Open Data Contract Standard, Linux Foundation, Apache 2.0).Contracts live as YAML files in each spoke repository under contracts/. They are validated automatically on every PR by the hub CI. ODCS is chosen because:
    • It is an open standard under Apache 2.0 licence, avoiding vendor lock-in.
    • It natively supports a regulatory SLA driver field, making regulatory sensitivity a first-class concept rather than a custom extension.
    • The datacontract-cli tooling enables automated validation in CI/CD with no additional infrastructure.
    • It is compatible with Databricks' own recommendation to use YAML-based contracts in Unity Catalog environments.

The canonical ODCS repository and schema are available at:
https://github.com/bitol-io/open-data-contract-standard

- The hub will adopt a proactive role in enabling high-quality, easy to create data products, as specified in the Golden Path principle. Here is what that means for this platform:

    - The hub provides a base contract template. Domain contracts extend it. Tier is determined by two boolean flags: glp_applicable and submission_bound.
    Fields mandatory in all tiers
    | Field | Purpose |
    |---|---|
    | id, name, version, domain, status | Identity and lifecycle |
    | team (named individual, not alias) | Accountability |
    | schema with field descriptions | Enables test generation and UC documentation |
    | quality (≥1 expectation) | Minimum quality bar |
    | lineage.sources | Cross-domain impact analysis |
    | governance.access_tier | Drives UC permission grants |
    | governance.glp_applicable | Triggers GLP audit trail controls |
    | governance.submission_bound | Triggers 25-year retention and immutable audit log |
    | provenance.source_version_or_date | Version pin — required for FAIR reproducibility |
    | quality_tier.known_limitations | Non-nullable. Prevents downstream misuse. |
    Tier-specific additions
    Tier 1 — Exploratory (glp_applicable: false, submission_bound: false)
    Applies to: Discovery, Translational Science
    Additional fields:
    ```yaml
    provenance.source_type: public_database_bulk | api_incremental | internal_experiment | manual_upload
    provenance.reproducibility_notes: how to regenerate the dataset
    quality_tier.validation_status: exploratory | validated
    ```
    Tier 2 — GLP-ready (glp_applicable: true, submission_bound: false)
    Applies to: Discovery (submission-bound experiments), Translational Medicine
    Additional fields beyond Tier 1:
    ```yaml
    experimental_context.study_id: ELN reference
    experimental_context.protocol_id: SOP identifier
    experimental_context.instrument_id
    experimental_context.analyst: named individual
    quality_tier.validation_status: must be glp_compliant
    ```
    Tier 3 — Regulatory (glp_applicable: true, submission_bound: true)
    Applies to: Clinical Development, Biostatistics, Regulatory Affairs
    Additional fields beyond Tier 2:
    ```yaml
    cdisc.standard: SDTM | ADaM | CDASH
    cdisc.version: e.g. 2.1
    cdisc.conformance_guide_version: FDA Technical Conformance Guide version
    sla.driver: must be regulatory
    archival.retention_period: 25 years (fixed — ICH E6)
    archival.archive_format: SAS_XPT_v5 (current FDA requirement)
    ```
    Enforced constraint: submission_bound: true requires glp_applicable: true. CI fails if violated.

    ### validate-contracts.yml
    Runs check_hub_fields.py and datacontract lint on every PR touching contracts/**. Blocks merge if: any mandatory field is null, known_limitations is empty, or submission_bound: true without glp_applicable: true.
    ### deploy-bundle-templates.yml
    On merge to main, syncs bundle-templates/ to /Shared/hub/bundle-templates in the Databricks workspace. Domain teams run databricks bundle init [hub-template-url] to scaffold a new data product. Templates bake in: catalog/schema naming convention, four-task pipeline structure (bronze → silver → validate_gx → publish_gold), table property stamping from contract metadata, and GRANT execution to declared consumer groups at publish time.
    ### audit-permissions.yml
    Runs weekly. Calls audit_uc_permissions.py, which compares uc-permissions/neuroscience_workspace.yaml against actual Unity Catalog state via the Databricks SDK. Fails the action if drift is detected. uc-permissions/ is the only permitted source of truth for permissions — notebook GRANT statements are not used.
    ### _hub_base_template.yaml
    The ODCS base contract. All spoke contracts extend this. Contains all mandatory fields with null defaults. Commented instructions for each field. The schema for datacontract lint validation is pinned to ODCS v3.1.0.
    ### generate_contract_tests.py
    Reads any ODCS contract YAML and outputs a Great Expectations expectation suite covering: required fields non-null, numeric fields within declared ranges, enum fields within declared value sets, row count within mustBeBetween bounds, release version matches source_version_or_date. Domain teams do not write these tests — they are generated automatically when the contract is valid.
    ### structural_tests.py
    Generic Delta table checks that run against every gold table regardless of domain: primary key not null and unique, no 100% null columns, schema matches contract declaration, table properties match contract metadata.
    ### regression_tests.py
    Cross-release checks: row count has not dropped >10% from previous release, primary keys from the previous release are still present, score distributions have not shifted beyond declared thresholds. Requires a baseline file per data product stored in the spoke repo.
    ### pharma_workspace.yaml
    Declares the complete permission model for all catalogs. Group-based, not user-based. Protected branch — changes require PR review. The pattern per catalog: BROWSE to all-neuroscience-users, SELECT on gold to declared reader groups, full pipeline access to service principal only.

## Consequences
The hub test framework covers structural and contract compliance tests automatically. Scientific assumption tests (filter thresholds, join logic, biological validity of derived fields) are not covered and must be written by the data product owner in the spoke repository. This is a documented gap, not an oversight.
The free tier constraint (one workspace, no account console) means Terraform-based provisioning cannot be executed. uc-permissions/ serves as the IaC specification; permissions are applied manually until a paid tier enables Terraform automation. This is accepted risk for demonstrator scope.

Three residual risks are accepted with mitigations in place. First, domain owners may fill known_limitations mechanically with boilerplate language. CI rejects null values but cannot enforce quality of prose — this requires human judgment at PR review. Second, hub-generated tests cover structural and contract compliance but not scientific correctness: a test that a score falls within [0,1] cannot verify that the scoring logic is biologically valid. Domain owners are responsible for scientific assumption tests in their spoke repositories; this is documented in the hub README. Third, permission drift is detected weekly but not in real time — a misconfigured grant could persist for up to seven days before the audit action catches it. This is accepted for demonstrator scope; a production deployment would require event-driven permission monitoring.
